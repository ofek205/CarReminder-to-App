# אפיון — התחזות אדמין 1:1 (Approach B)

> נוצר 2026-07-24. יורש את `admin-view-as-spec.md` ו-`admin-view-as-full-visibility-spec.md`.
> סטטוס: **אפיון לאישור Ofek** — לפני כתיבת קוד.

## 1. המטרה

אדמין רואה ועושה **בדיוק** מה שהמשתמש רואה ועושה. אפס פערים — כולל בטבלאות שייווצרו בעתיד.

## 2. למה המודל הקיים לא יכול להגיע לשם

היום (`Approach A / split model`) האדמין שומר את ה-JWT של עצמו, והשרת מעניק גישה דרך פתחי מילוט:

```
is_viewing(account_id)        → ~9 טבלאות מבוססות-חשבון
is_viewing_user(user_id)      → 3 טבלאות אישיות (נוסף 54fed04)
admin bypass ללא תנאי         → 5 טבלאות ליבה
```

**זו רשימת היתר.** ברירת המחדל של כל טבלה חדשה היא "בלתי-נראית ב-view-as". כדי להגיע ל-1:1 היה צריך policy לכל טבלה, לכל פעולה (`select`/`insert`/`update`/`delete`), ומשמעת מושלמת לנצח.

הפער הזה כבר ייצר שני באגים בייצור: ה-Frankenstein gap (נתונים של אדמין ושל היעד מעורבבים באותו מסך), וכתיבה שכמעט לא עובדת ב-view-as.

> **1:1 היא תכונה של היעדר רשימה. רשימת היתר יכולה להתקרב אליה, אך לעולם לא להיות היא.**

## 3. העיקרון

במקום להרחיב הרשאות לאדמין — **להנפיק לו זהות של היעד, לזמן קצוב**.

```
היום:        admin JWT   →  RLS: "יש היתר מיוחד?"  →  תלוי בטבלה
Approach B:  target JWT  →  RLS: הכללים הרגילים    →  1:1 מובנה
```

`auth.uid()` הוא המשתמש → **כל policy קיימת ועתידית עובדת בלי שינוי. אפס תחזוקה.**

## 4. מבנה הטוקן

JWT חתום ב-JWT secret של הפרויקט, עם תביעה נוספת:

```jsonc
{
  "sub":             "<target_user_id>",   // RLS רואה את היעד
  "role":            "authenticated",
  "impersonated_by": "<admin_user_id>",    // טביעת אצבע — נשארת ב-token
  "session_id":      "<admin_view_sessions.id>",
  "exp":             <now + 15min>
}
```

`impersonated_by` היא מה שמאפשר ייחוס **בלי לוותר על 1:1**. Postgres קורא אותה ישירות:

```sql
auth.jwt() ->> 'impersonated_by'
```

## 5. הזרימה

### כניסה
1. אדמין לוחץ "צפה כמשתמש" (הממשק קיים)
2. `admin_start_view` יוצר שורת סשן — **קיים היום, לא משתנה**
3. הלקוח קורא ל-edge function `admin-impersonate` עם ה-JWT של האדמין
4. הפונקציה מאמתת **שניים**: `is_admin()` **וגם** שורת סשן פעילה שהיעד שלה תואם
5. חותמת טוקן, מחזירה אותו + `expires_at`
6. הלקוח מחליף את הטוקן ב-Supabase client. הטוקן של האדמין נשמר בזיכרון בלבד

### יציאה
1. `admin_end_view` סוגר את הסשן
2. הלקוח משליך את טוקן ההתחזות ומשחזר את של האדמין
3. `queryClient.clear()` + ניקוי מטמון URL חתומים — **קיים היום ב-`exitViewAs`**

### תפוגה
טוקן חתום-עצמית **אין לו refresh**. ב-15 דקות הוא פג והלקוח נופל חזרה לאדמין. חידוש = קריאה חוזרת ל-function, שמאמתת מחדש שהסשן עדיין פעיל.

## 6. ייחוס

טריגר על טבלאות רגישות מחתים `acting_admin_id`:

```sql
create or replace function public.stamp_acting_admin()
returns trigger language plpgsql as $$
begin
  new.acting_admin_id := nullif(auth.jwt() ->> 'impersonated_by', '')::uuid;
  return new;
end $$;
```

- **גלוי לאדמינים בלבד** — המשתמש לא רואה את העמודה
- `null` בכתיבה רגילה → אפס השפעה על משתמשים
- טבלאות מועמדות: `vehicles`, `documents`, `maintenance_logs`, `accidents`, `vehicle_expenses`

## 7. דרישות אבטחה — בלתי-מתפשרות

1. **ה-JWT secret חי אך ורק ב-edge function.** אם הוא נוגע ב-bundle של הלקוח, כל משתמש יכול להתחזות לכל אחד. זה החוט היחיד שמחזיק את המודל.
2. **אימות כפול.** `is_admin()` לבדו לא מספיק — חייבת להיות שורת סשן פעילה. הסשן הוא פרימיטיב הגישה, לא דגל קוסמטי.
3. **תפוגה קצרה.** 15 דקות, מסונכרנת עם הסשן.
4. **תיעוד לכל הנפקה.** דרך `securityLog.ts` הקיים — אירוע חדש `impersonation_issued`.
5. **אין הנפקה לאדמין אחר.** יעד שהוא עצמו אדמין → דחייה. מונע הסלמת הרשאות רוחבית.

## 8. מצבי כשל

| תרחיש | התנהגות |
|---|---|
| הסשן פג באמצע | הטוקן פג תוך 15 דק'; חידוש נכשל; הלקוח חוזר לאדמין |
| ה-function לא זמינה | הכניסה נכשלת. **אין נפילה חזרה למודל הישן** |
| היעד נמחק מ-auth.users | חתימה נכשלת; שגיאה מפורשת |
| האדמין מאבד הרשאות תוך כדי | הטוקן הקיים תקף עד לתפוגה — מגבלה מקובלת ב-15 דק' |

## 9. מה נבנה

| # | רכיב | הערה |
|---|---|---|
| 1 | `supabase/functions/admin-impersonate/index.ts` | לפי הדפוס של 16 ה-functions הקיימות |
| 2 | החלפת טוקן ב-`viewAsState.js` | הרחבה, לא כתיבה מחדש |
| 3 | `supabase-impersonation-attribution.sql` | עמודות + טריגר |
| 4 | `impersonation_issued` ב-`securityLog.ts` | הרחבת הטקסונומיה |

**מה שנשאר בלי שינוי:** `admin_view_sessions`, `admin_start_view` / `admin_end_view`, ממשק הכניסה, מסך `AdminViewSessions`.

**מה שמתיישן:** `is_viewing()` / `is_viewing_user()` וה-policies שלהן. **לא מוחקים בשלב ראשון** — משאירים כרשת ביטחון עד שהמודל החדש יוכח.

## נספח — למה לא לתקן את המודל הקיים

הוצע להמשיך ולהוסיף policies טבלה-טבלה. נדחה: זו בדיוק העבודה שנכשלה פעמיים. הבדיקה מול הייצור ב-2026-07-24 מצאה 21 policies שדולפות ב-6 טבלאות במסלול ההזמנות — כולן נכתבו בכוונה טובה, וכולן פספסו תנאי אחד. מודל שנכשל כשמישהו שוכח שורה אינו מודל אבטחה; הוא רשימת מטלות.
