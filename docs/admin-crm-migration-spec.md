# מפרט מעבר בטוח למערכת הניהול וה־CRM החדשה

עודכן: 12 בספטמבר 2026  
סטטוס: תכנון טכני ומוצרי. מסכי הניהול הפעילים לא שונו.

מסמך זה משלים את [תכנון המבנה והמוצר](./admin-crm-redesign-plan.md). הוא מגדיר איך לבנות את המערכת החדשה בהדרגה, בלי לאבד יכולות ובלי לסכן נתוני משתמשים.

## מסקנת הבדיקה המעמיקה

אפשר לבנות מערכת ניהול חדשה בלי לכתוב מחדש את כל המוצר. הדרך הבטוחה היא להשאיר תחילה את מקורות הנתונים והפעולות הקיימים, לבנות מעליהם שכבת API אחידה וממשק חדש במקביל, ולהחליף כל אזור רק אחרי בדיקת תאימות מול המסך הישן.

הסיכון העיקרי אינו העיצוב. הסיכון נמצא בחיבורים הסמויים בין הדפים, בחלק מהפעולות שעדיין עוקפות את שכבת הפקודות, ובהיעדר בדיקות ייעודיות למסכי Admin.

### נתונים מהקוד הקיים

- 15 נתיבי ניהול רשומים: 14 נתיבי `Admin*` ועוד `EmailCenter`.
- קבצי הליבה שנבדקו מכילים יחד כ־10,500 שורות.
- `AdminDashboard.jsx` לבדו מכיל 2,559 שורות ומשמש גם כמקור לרכיבים שמיובאים בדפים אחרים.
- `AdminUserDrawer.jsx` מכיל 2,199 שורות ומרכז כמעט את כל הפעולות הרגישות על לקוח וחשבון.
- `AdminUsers` מייבא את רשימת החשבונות מתוך `AdminDashboard`.
- `EmailCenter` מייבא את תיבת הפניות מתוך `AdminDashboard`.
- לא נמצאו בדיקות יחידה או בדיקות מסך שמיועדות ישירות לאזור הניהול.
- קיימים שערי build, lint, unit tests, query timeout וזהות view-as, אך הם אינם מוכיחים שתהליך ניהולי מלא עדיין עובד.
- קבצי SQL מוחלים ידנית ואין migration runner. סביבת staging ו־production חולקות כרגע מסד נתונים, ולכן אסור להשתמש במעבר הממשק כתירוץ לשינוי סכימה מוקדם.

### היקף הבדיקה המשלימה

המיפוי אינו מוגבל לשורות התפריט. נבדקו גם:

- כל הקבצים בשם `Admin*`
- כל רכיבי `src/components/admin`
- hooks של מיילים והרשאות
- `WorkspaceContext` וזרימת view-as
- שימושים ב־`useIsAdmin` מחוץ למסכי Admin
- Edge Functions שנקראות מממשק הניהול
- יכולות ציבוריות ששמן יוצר רושם שהן חלק מה־Admin
- שאילתות ופעולות ישירות שאינן עוברות ב־DAL

## שבעה פערים שחייבים לטפל בהם לפני החלפת מסכים

### 1. מקור הרשאת Admin אינו תואם למסך שינוי תפקיד

ההרשאה האפקטיבית נקבעת בצד השרת באמצעות רשימת מיילים ב־`is_admin()`. הפעולה `admin_set_role` משנה `raw_user_meta_data.role`, אך השדה הזה אינו עוד מקור סמכות. לכן כפתור שמציג „הפוך לאדמין” עלול להצליח טכנית בלי לתת הרשאת ניהול אמיתית.

החלטה:

- בשלב הראשון מסתירים או משנים את שם הפעולה כך שלא תבטיח הרשאה שאינה ניתנת.
- לפני הוספת מנהלים נוספים בונים טבלת תפקידי ניהול בצד השרת ו־RPC ייעודי.
- אין להחזיר הסתמכות על metadata שניתן לשינוי מצד הלקוח.

### 2. Feature flags קיימים אינם מתאימים לבחירה בין V1 ל־V2

`useFeatureFlag` מאפשר לאדמין תמיד לעבור את הדגל. זה נכון לבדיקת פיצ'רים של משתמשים, אך לא מאפשר לכבות את קונסולת V2 עבור מנהל במקרה תקלה.

החלטה:

- החשיפה הראשונה תתבצע בעזרת משתנה build נפרד, למשל `VITE_ADMIN_CONSOLE_V2`, שמופעל רק בפריסת staging.
- הנתיב החדש לא יחליף שום נתיב קיים ולא יופיע בתפריט production בשלב הראשון.
- בהמשך יתווסף מתג חזרה ל־V1 למנהל. הבחירה תישמר מקומית, בעוד שמתג החירום יישאר ברמת הפריסה.

### 3. פעולות Admin אינן עוברות כולן באותה שכבה

רוב הפעולות הרגישות כבר רשומות ב־DAL, אך עדיין קיימות פעולות ישירות:

- סימון התראה כטופלה
- ניהול חריגות ותוכניות
- סיום סשן view-as בכוח
- שינוי סטטוס פנייה
- שינוי feature flags של AI
- חלק מפעולות התקשורת והגדרות המייל

החלטה:

- לפני העברת UI, כל פעולה שמשנה מידע תקבל command רשום אחד.
- כל פקודת Admin תשתמש ב־`adminSupabase`, למעט פעולות משתמש רגילות שהוגדרו במפורש אחרת.
- ה־UI החדש לא יקרא `.insert()`, `.update()`, `.delete()` או RPC משנה מידע ישירות.

### 4. כיסוי יומן הפעולות חלקי

קיים `admin_audit_log` בלתי ניתן לשינוי, וחלק מה־RPCs כותבים אליו. אין הוכחה שכל פעולה ניהולית חשובה נרשמת בו. פעולות ישירות על טבלאות עלולות לא להירשם כלל.

החלטה:

- כל פעולה רגישה תקבל אירוע audit עם מבצע, יעד, סיבה, ערך קודם, ערך חדש וזמן.
- לא כותבים audit מהדפדפן. ה־RPC שמבצע את השינוי כותב את הרשומה באותה טרנזקציה.
- פעולות בסיכון גבוה דורשות שדה סיבה לפני שליחה.

### 5. ניהול גרסאות מופרד חלקית בלבד בין iOS ל־Android

מספר הגרסה האחרונה, גרסת המינימום ושליחת התראת `app_update` כבר מקבלים `platform`. הודעת „מה חדש” עדיין נשמרת במפתח גלובלי אחד בשם `release_announcement`, ולכן היא מוצגת בלי קשר לפלטפורמה או לגרסה שעלתה בחנות.

קיים גם מקרה קצה חשוב: `broadcast_app_update` בוחר משתמשים שיש להם מכשיר בפלטפורמת היעד, אך `dispatch-push` שולח לאחר מכן לכל ה־device tokens של אותו משתמש. משתמש שמחובר גם ב־iPhone וגם ב־Android עלול לקבל Push של גרסת iOS במכשיר Android. רשימת ההתראות והפעמון אינם מסננים כיום `app_update` לפי `data.platform`.

החלטה:

- לכל פלטפורמה יהיה תהליך שחרור עצמאי לחלוטין.
- הודעת „מה חדש”, הודעת הפעמון, ה־Push, מספר הגרסה ומועד הפרסום יקושרו לאותה פלטפורמה.
- `dispatch-push` יסנן tokens לפי `data.platform` כאשר מדובר בהתראת גרסה.
- הפעמון ודף ההתראות יציגו `app_update` רק כאשר `data.platform` תואם למכשיר הנוכחי.
- הודעת „מה חדש” לא תוצג ב־Web ולא תוצג בפלטפורמה שהגרסה שלה עדיין לא פורסמה.

### 6. טלמטריה, באגים וטעויות משתמש מעורבבים באותו מקור

`app_errors` משמשת כיום בו זמנית לקראשים, כשלי query, הודעות שהוצגו למשתמש, דיווחים ידניים ושאילתות איטיות. מסך הבריאות סופר כמעט את כל הרשומות כ„שגיאות”, ומסך הבאגים מציג אותן כרשומות עצמאיות. בפועל קיימים שלושה מקורות רעש:

- `slow_query` נוצר לאחר 5 שניות של זמן קיר בצד הלקוח, כולל זמן רשת. זו אינדיקציית ביצועים ולא הוכחה לבאג או לבעיה במסד הנתונים.
- `toastError` משמש גם לשגיאות אמיתיות וגם לוולידציה צפויה כמו „יש לבחור רכב”, „יש להזין טלפון” או „הסכום חייב להיות גדול מ־0”. ולידציה כזו אינה תקלה במוצר.
- `SafeComponent` בולע קריסה, כותב רק `console.warn` ומחזיר `null`. כך רכיב עלול להיעלם למשתמש בלי דרך התאוששות ובלי אירוע שניתן לטפל בו.

גם ההתראה `slow_query_storm` ההיסטורית אינה אות אמין: קיים migration שמגדיר את `alert_mute_slow_query_storm` להשתקה, והטקסט שלה עדיין מציין שלוש שניות אף שסף הקוד הוא חמש שניות. יש לוודא מול סביבת היעד שה־migration אכן הוחל.

החלטה:

- נשמור את `app_errors` כמקור raw לצורך תאימות, אך ה־UI החדש יסווג ויקבץ אירועים לפני הצגתם.
- נפריד בין תקלה, כשל פעולה, ביצועים, חיבור, כלל עסקי, ולידציה ודיווח משתמש.
- ולידציה תוצג ליד השדה ולא תירשם כבאג. הודעות צפויות כמו הרשאה חסרה, מגבלת תוכנית או מצב Offline יקבלו מצב מוצר ייעודי.
- שאילתה איטית תיכנס למסך ביצועים. timeout או כשל חוזר שמשפיע על משתמשים ייכנסו לתור התקלות.
- קריסה שנבלעה ב־`SafeComponent` תקבל דיווח, fallback קטן ופעולת ניסיון מחדש.
- מדד בריאות המערכת לא יעלה בגלל ולידציות או שאילתות איטיות ממכשיר בודד ברשת חלשה.

### 7. שליחת הודעות מפוצלת בין כמה ממשקים וחוזי שליחה

כיום אין פעולה אחת ברורה בשם „שלח הודעה”. מייל ישיר נשלח מתוך `AdminUserDrawer`, מענה להתראה נבנה שוב בתוך `AdminAlerts`, הפצה רחבה נמצאת ליד תבניות המייל, פופ־אפים מחזיקים מנגנון קהל עצמאי, ופניות „צור קשר” נענות באמצעות `mailto:` חיצוני. הדבר יוצר כמה פערים:

- `dispatch-broadcast` תומך רק בכל המשתמשים הזכאים לתבנית ואינו מקבל segment, חשבון, פלטפורמה או רשימת משתמשים.
- בדיקת תבנית דורשת מהמנהל לערוך JSON של משתנים במקום טופס אנושי.
- שליחת `admin_direct` יוצרת הודעה באפליקציה רק לאחר שהמייל הצליח. כשל ב־Resend יכול למנוע גם ערוץ פנימי שהיה יכול להצליח.
- טופסי השליחה הישירה משוכפלים ואינם מציגים היסטוריית שיחה או סטטוס מסירה מלא בהקשר של הלקוח.
- לחיצה על „השב” בפניית צור קשר פותחת תוכנת מייל חיצונית ומסמנת את הפנייה כנענתה עוד לפני שנשלחה תשובה.
- לוג השליחה בנוי סביב מיילים ולא סביב משתמש, קמפיין ומספר ערוצים.
- קיימים במחרוזות היוצאות שמות שונים כמו `CarReminder` ואף `CardDocs`, למרות שהמותג שנקבע הוא `Car Reminder`.
- בקוד ההפצה השיווקית כתובת השולח החוקית עדיין ריקה ומסומנת כ־TODO; יש להשלים פרטי עסק לפני הפצה שיווקית נוספת.

החלטה:

- נבנה composer אחד לכל הודעה יזומה, ונפתח אותו גם מתוך כרטיס לקוח, פנייה או incident עם context מוכן.
- קהל ייפתר בצד השרת ל־audience snapshot לפני אישור. הלקוח לא ישלח מערך נמענים שהוא הרכיב בעצמו.
- כל ערוץ ירוץ כמשימת מסירה עצמאית. כשל מייל לא ימנע פעמון או Push, ותוצאת כל ערוץ תוצג בנפרד.
- תבניות, קהלים, קמפיינים, אוטומציות ופניות יישארו ישויות נפרדות, אך ישתמשו באותו חוזה תוכן, קהל, הרשאה, תצוגה מקדימה ו־audit.
- פנייה תסומן כנענתה רק לאחר שליחה מוצלחת או שינוי סטטוס מפורש.
- שם המותג ופרטי השולח יגיעו מהגדרת מערכת אחת ולא ממחרוזות מקומיות במסכים.

## חוזה התאימות

אסור להסיר או להעביר מסך לפני שכל היכולות שלו מופיעות במטריצה ומקבלות בדיקת תאימות.

| יכולת קיימת | מקור נוכחי | יעד במערכת החדשה | תנאי תאימות |
| --- | --- | --- | --- |
| תורי עבודה וספירות פתוחות | `admin_action_inbox` | מרכז עבודה | אותן ספירות מול V1 באותו זמן ובאותם פילטרים |
| מצב מערכת | `admin_health_status`, `admin_health_drilldown` | תפעול > בריאות | כל probe, סטטוס ופירוט נשמרים |
| רשימת אנשים | `admin_user_list` | לקוחות > אנשים | אותו מספר רשומות, חיפוש, פילטרים, מיון וייצוא |
| רשימת חשבונות | `admin_list_accounts` | לקוחות > חשבונות | כל חשבון נפתח לאותו dossier |
| פרטי חשבון | `admin_account_details` | עמוד לקוח | כלי תחבורה, מסמכים, חברים, הוצאות ופעילות מופיעים |
| חשבונות של משתמש | `admin_user_accounts` | עמוד לקוח | מעבר בין חשבונות שומר הקשר ואינו מערבב נתונים |
| עדכון כלי | `admin_update_vehicle` | עמוד לקוח > כלים | אותם שדות, validation ורענון רשימות |
| מחיקת כלי יחיד או מרובה | `admin_delete_vehicle(s)` | עמוד לקוח > כלים | preview, אישור, תוצאה ו־audit |
| החלפת בעל חשבון | `admin_set_account_owner` | עמוד לקוח > חברים והרשאות | הצגת בעלים קודם, השפעה וחברי החשבון לאחר הפעולה |
| מחיקת חשבון או משתמש | `admin_delete_account`, `admin_delete_user_full` | תפריט פעולות רגישות | אישור מודגש, סיבה, תוצאה ויכולת איתור ביומן |
| הערה פנימית | `admin_set_user_note` | עמוד לקוח > הערות | שמירה, עריכה, זמן ומנהל אחרון |
| תוכנית, חריגות ו־grace | RPCs של monetization | עמוד לקוח > תוכנית | אותו effective plan לפני ואחרי וכל שינוי נרשם |
| בקשות עסקיות | list, approve, deny RPCs | לקוחות > בקשות הצטרפות | סטטוסים, הערת סקירה והתראה למבקש נשמרים |
| צפייה כמשתמש | start/current/end/force-end | עמוד לקוח + תפעול | בידוד זהות, באנר קבוע, יציאה אמינה וסיום בכוח |
| אנליטיקה | summary + drilldown RPCs | מוצר וצמיחה | טווחי זמן ופילוחים מחזירים אותם ערכים |
| שימוש ב־AI | `ai_usage_logs` ו־RPCs | מוצר וצמיחה > AI | מכסות, ספקים, surfaces ומשתמשים מובילים נשמרים |
| בחירת ספק AI | `set_ai_provider` | הגדרות > AI | אותו ספק נבחר לכל feature ו־audit קיים |
| באגים | `app_errors` + local fallback | תפעול > אירועים | נשמרת הבחנה בין remote ל־local וכל הפילטרים |
| התראות | `admin_alerts`, acknowledge RPC | תפעול > אירועים | חומרה, מקור, acknowledged והספירה בתפריט נשמרים |
| גרסאות ועדכון חובה | version RPCs ו־app_config | תפעול > גרסאות | לכל פלטפורמה נשמרים latest, minimum, סטטוס והפעלה עצמאית |
| הודעת „מה חדש” | `release_announcement` גלובלי | תפעול > גרסאות > iOS/Android | מוחלף בשתי הודעות עצמאיות המקושרות לפלטפורמה ולגרסה |

## יכולות מחוץ לתפריט הניהול

אלה אינן חלק ישיר מה־CRM, אך שינוי מעטפת הניהול עלול להשפיע עליהן ולכן הן נכנסות לחוזה השימור.

### חוות דעת

`AdminReviews` פתוח גם לאורחים ולמשתמשים ומאפשר צפייה וכתיבה. זהו דף מוצר ציבורי ששמו מטעה, ולא כלי ניהול. במסגרת המעבר:

- הדף הציבורי נשאר פעיל ומקבל שם נתיב שאינו Admin.
- ניהול או moderation של חוות דעת, אם יתווסף, יהיה מסך נפרד תחת „מוצר וצמיחה > פידבק”.
- לא מוסיפים לדף הציבורי הרשאת Admin רק בגלל שמו הנוכחי.

### בטיחות ילדים ברכב

`SafetyReminder` מוצג כרגע רק לאדמין מתוך Settings לצורך dogfooding של פיצ'ר שעדיין מוגן. הוא אינו מסך ניהול לקוחות.

- הוא נשאר מחוץ ל־AdminShell.
- הרשאת הניסוי והחסימה למשתמשים רגילים נשמרות.
- שינוי מערכת ההרשאות של Admin מחייב בדיקה שהגישה לניסוי לא נפתחה בטעות.

### קהילה ודיווחים

קיימים `reported_posts`, חסימות משתמש אישיות ו־`community_blocked_users`, אך לא נמצא תור moderation מלא וברור בממשק Admin הנוכחי. קיימת הערת קוד שטוענת שהדיווחים מגיעים לדשבורד, אך לא נמצאה קריאה פעילה ל־`reported_posts` בתוך `AdminDashboard`.

החלטה:

- שימור זרימת הדיווח והחסימה של משתמשים הוא תנאי בסיס.
- מוסיפים ב־P1 תור „דיווחי קהילה” תחת תפעול, עם צפייה בתוכן, סיבה, מדווח, מחבר ופעולת טיפול.
- מחיקה או חסימה גלובלית דורשות RPC, הרשאת שרת ו־audit.

### התנהגות ניווט והרשאה

- מנהל שמגיע לשורש המערכת מופנה כיום ל־`AdminHome`; V2 צריך לשמור את ההפניה לפי build flag.
- עמוד 404 מציג למנהל קיצור חזרה לאזור הניהול.
- מונה ההתראות בתפריט נטען בנפרד ומתרענן; הוא חלק מחוזה המעטפת.
- בזמן view-as תפריט הניהול מוסתר ו־`ViewAsRouteGuard` מונע כניסה ישירה לנתיב Admin.
- הודעות `admin_direct` מוצגות למשתמש ברכיב `AdminMessageDialog`; זהו צד הלקוח של פעולת השליחה וצריך להיבדק יחד איתה.

## מערכת באגים, ביצועים וניהול פעילות

### עקרון הסיווג

לא כל הודעה אדומה היא באג, ולא כל אירוע טכני צריך להגיע למנהל. שכבת הסיווג החדשה תשתמש במודל הבא:

| סוג | דוגמה | מה המשתמש רואה | היכן מנוהל |
| --- | --- | --- | --- |
| ולידציה | חסר מספר טלפון או לא נבחר רכב | הסבר ליד השדה ומיקוד בשדה | לא נרשם כבאג |
| כלל עסקי צפוי | אין הרשאה, מגבלת תוכנית, כלי אינו בחשבון | הודעה ברורה עם הפעולה האפשרית | פעילות מוצר; אירוע אבטחה רק אם חריג |
| חיבור | Offline, מעבר רשת, timeout זמני | מצב Offline או Retry, תוך שמירת טיוטה כשאפשר | מדדי חיבור; לא אירוע בודד בתור באגים |
| ביצועים | query הסתיים בין 5 ל־8 שניות | בדרך כלל ללא הודעה | מסך ביצועים |
| כשל פעולה | שמירה, מחיקה או העלאה לא הצליחו | הודעה ממוקדת, Retry וקוד פנייה | תור השפעה על משתמשים |
| timeout | query עבר את מגבלת 8 השניות | מצב שגיאה עם ניסיון מחדש | תור תקלות וגם ביצועים |
| crash | רכיב או עמוד קרס | fallback יציב עם Retry וחזרה | תור תקלות, חומרה גבוהה |
| דיווח משתמש | „לחצתי על שמירה ולא קרה כלום” | אישור וקוד דיווח | תור דיווחים |
| כשל תפעולי | Push, מייל, Webhook או cron נכשלו | אין הודעה למשתמש אלא אם הפעולה שלו הושפעה | תור משלוחים ותפעול |

הסף של 5 שניות מתאר זמן כולל במכשיר, לרבות רשת. הוא לא מאפשר להסיק לבדו שהמסד איטי. כדי לזהות בעיית שרת יש לצרף מדידת backend או Postgres ולהשוות אותה לזמן הלקוח.

### מבנה מסך התפעול

בראש המסך יוצגו ארבעה מדדים בלבד: אירועים פתוחים, משתמשים שנפגעו ב־24 שעות, regressions מאז הגרסה האחרונה ופעולות משלוח שנכשלו. מתחתיהם יהיו טאבים עצמאיים:

1. **השפעה על משתמשים**: קראשים, timeouts וכשלי שמירה או טעינה.
2. **דיווחים**: דיווחים יזומים שהגיעו מהאפליקציה.
3. **ביצועים**: p50, p95 ו־p99 לפי query label, מסך, פלטפורמה וגרסה.
4. **משלוחים ואוטומציות**: Push, מייל, Webhook ו־cron.
5. **נפתרו**: היסטוריה מלאה וחיפוש.

ברירת המחדל לא תהיה רשימת `app_errors` גולמית. הרשומות יקובצו ל־incident לפי חתימה יציבה: סוג, הודעה מנורמלת, action, route ומקור stack. מספרים, מזהים ותאריכים ישתנו למשתנים לפני יצירת החתימה כדי שאותה תקלה לא תתפצל למאות קבוצות.

כל שורת incident תציג:

- כותרת אנושית ותיאור קצר של ההשפעה
- חומרה, סטטוס ואחראי
- מספר מופעים, משתמשים וסשנים ייחודיים
- פלטפורמות, גרסאות, routes וחשבונות שנפגעו
- זמן הופעה ראשון ואחרון וסימון „חזר אחרי שנפתר”
- שינוי בגרסה או בפריסה שסמוך אליו התחילה הבעיה, כאשר הנתון קיים

פתיחת incident תציג timeline, דוגמאות אירוע, breadcrumbs מסוננים, stack, פרטי רשת וביצועים וקישור ללקוח רק למנהל מורשה. פעולות הטיפול יהיו שיוך אחראי, שינוי חומרה, הוספת הערה פנימית, מעבר סטטוס, קישור לפריסה וסגירה עם סיבה.

### מחזור חיים של incident

הסטטוסים יהיו `new`, `triaged`, `in_progress`, `monitoring`, `resolved` ו־`ignored`. סימון `resolved` הקיים ימופה בשלב התאימות לסטטוס `resolved`, אך לא יהיה עוד השדה היחיד שמתאר טיפול.

פתיחה אוטומטית של incident תקרה רק באחד התנאים הבאים:

- crash ראשון בחומרה קריטית
- timeout שחזר אצל כמה משתמשים או סשנים בחלון זמן מוגדר
- שיעור כשל בפעולה עלה ביחס לבסיס ההיסטורי
- אותו כשל חזר לאחר שסומן כנפתר
- דיווח משתמש נקשר לחתימה שכבר קיימת

שאילתה איטית בודדת לא תפתח incident. התראה תיפתח רק כשיש חריגה עקבית לפי label ובכמה רשתות או משתמשים, או כשמדידת השרת מאשרת האטה. כל סף יהיה הגדרה גלויה ולא טקסט קשיח בתוך SQL.

### חוויית משתמש בזמן שגיאה

שגיאות יוצגו לפי המקום והפעולה:

- ולידציה נשארת ליד השדה, עם טקסט שמסביר כיצד לתקן.
- כשל פעולה משאיר את הטופס והקבצים במקום ומציע „נסה שוב”.
- מסך שלא נטען מציג Retry, חזרה ושימוש בנתונים אחרונים כאשר הדבר בטוח.
- שגיאה חוזרת מציעה „דווח על תקלה” בלי לפתוח חלון בכוח.
- למשתמש לא יוצגו stack, שם טבלה, query, SQL או הודעת שרת גולמית.
- לכל כשל אמיתי שנרשם ייווצר קוד פנייה קצר שאפשר למסור לתמיכה.

חלון הדיווח הקיים נשאר, אך יקבל בחירת נושא קצרה: טעינה, שמירה, נתונים שגויים, תצוגה או אחר. התיאור יישאר חופשי. route, גרסה, פלטפורמה, account, session ו־breadcrumbs יצורפו אוטומטית. צילום מסך או תוכן מסך יצורפו רק בבחירה מפורשת של המשתמש. לאחר שליחה יוצג מספר דיווח ולא רק הודעת „תודה”.

`PageErrorBoundary` לא יציג למשתמש את `error.message` הגולמי. `SafeComponent` לא יחזיר `null` בשקט: רכיב משני יקבל placeholder קטן וניסיון מחדש, והרכיב הקריטי יקדם את השגיאה ל־Page boundary.

### הפרדת פעילות, Audit וטלמטריה

„ניהול פעילות” יחולק לשלושה מקורות שאסור לערבב:

1. **פעילות לקוח**: כניסה, הוספת כלי, יצירת מסמך, עדכון טיפול, הזמנה או שימוש בפיצ'ר. המידע מוצג ב־timeline של הלקוח.
2. **Audit מנהלי**: מי שינה תוכנית, הרשאה, בעלות, feature flag או תוכן הודעה. האירוע נכתב בצד השרת ונשמר עם before/after וסיבה.
3. **טלמטריה טכנית**: query, crash, זמן תגובה, רשת ומשלוחים. המידע מוצג בתפעול ובריאות.

כך חיפוש פעילות של לקוח אינו מחזיר מאות slow queries, ומסך תקלות אינו מתמלא בפעולות עסקיות תקינות.

### מודל נתונים תואם לאחור

בשלב הראשון אין מוחקים רשומות מ־`app_errors`. נוסיף שכבת קריאה שמנרמלת כל רשומה לשדות הבאים:

```text
event_class: validation | business_rule | connectivity | performance |
             operation_failure | timeout | crash | user_report | delivery
fingerprint
outcome: success | degraded | failed
platform
app_version
route
action
query_label
duration_ms
account_id
user_id
session_id
occurred_at
```

לצורך workflow אפשר להוסיף בהמשך `admin_incidents` ו־`admin_incident_events`. הראשונה תחזיק סטטוס, חומרה, אחראי וחתימה; השנייה תקשר את ה־incident לאירועי raw. מידע אישי לא יוכנס לחתימה, ל־URL או לטקסט ההתראה.

### תיקוני בסיס לפני בניית המסך החדש

1. להוסיף API נפרד לוולידציה ולמצבי מוצר צפויים, ולהפסיק לשלוח אותם דרך `toastError`.
2. להעביר שגיאות ולידציה מרכזיות מ־toast לשדות הטופס.
3. להוסיף classifier מרכזי במקום סינון שונה בכל מסך ו־RPC.
4. להחריג `slow_query`, ולידציה ומצבי Offline ממדד „שגיאות ב־24 שעות”.
5. להחליף את טקסט „מעל 3 שניות” בערך שמגיע מהגדרה, אם מחזירים בעתיד את ההתראה.
6. לדווח על קריסות `SafeComponent` ולאפשר התאוששות.
7. למפות את 134 הקריאות הישירות ל־`toast.error` ואת 233 הקריאות ל־`toastError`; כשל אמיתי יתועד, הודעת מידע או ולידציה לא.
8. להוסיף `query_timeout` מפורש כדי שלא יסתמך על parsing של טקסט `supabase query timeout`.

### בדיקות קבלה לתחום

- הודעת „יש לבחור רכב” אינה יוצרת `app_errors` ואינה משנה את בריאות המערכת.
- query של 6 שניות נרשם כביצועים בלבד ואינו פותח incident.
- query שעובר 8 שניות מציג Retry, נרשם כ־timeout ומקובץ עם מופעים זהים.
- Offline אינו מייצר incident, והטיוטה נשמרת כאשר הזרימה תומכת בכך.
- אותה קריסה אצל מאה משתמשים מוצגת כ־incident אחד עם מאה משתמשים שנפגעו.
- קריסה שחזרה אחרי `resolved` מסומנת regression ונפתחת מחדש.
- דיווח משתמש מקבל מספר, מופיע בתור דיווחים ונקשר ל־incident תואם אם קיים.
- stack ופרטי שרת אינם מוצגים למשתמש.
- breadcrumbs אינם כוללים ערכי טפסים, מסמכים או מידע רגיש.
- מדד בריאות מבחין בין client latency לבין server latency.

## מערכת תקשורת ושליחת הודעות

### מבנה האזור

אזור התקשורת לא יהיה עוד אוסף טאבים טכניים. הניווט המשני יהיה:

1. **סקירה**: טיוטות אחרונות, שליחות מתוזמנות, קמפיינים פעילים, כשלים ונתוני 30 יום.
2. **תיבת פניות**: פניות נכנסות ושיחות עם לקוחות.
3. **קמפיינים**: הודעות יזומות, סטטוס ותוצאות.
4. **אוטומציות**: תזכורות, תנאים, תדירות והרצות.
5. **תבניות**: draft, published, היסטוריית גרסאות ותצוגה מקדימה.
6. **בתוך האפליקציה**: פופ־אפים, banners והודעות פעמון.
7. **מסירה**: כל ניסיונות המסירה והאירועים לפי ערוץ.

„פניות” ו„הודעות יזומות” לא ישתמשו באותו שם בתפריט. כך מנהל יבין אם הוא מטפל בשיחה שנכנסה או יוצר הודעה חדשה.

### כפתור „הודעה חדשה”

הכפתור יופיע בכותרת האזור ויהיה זמין גם מתוך כרטיס לקוח, חשבון, פנייה ו־incident. הוא יפתח wizard קצר עם שמירת טיוטה אוטומטית.

#### שלב 1: מטרה וסוג הודעה

- הודעת שירות אישית
- הודעה תפעולית חשובה
- עדכון מוצר או גרסה
- קמפיין שימוש והדרכה
- דיוור שיווקי

הבחירה תקבע אילו העדפות והגבלות חלות. הודעת שירות לא תסומן כשיווקית, והודעה שיווקית לא תוכל לעקוף opt-out.

#### שלב 2: קהל

אפשרויות הקהל יהיו:

- משתמש יחיד או כמה משתמשים שנבחרו
- חשבון עסקי וכל החברים או בעלי תפקידים מסוימים
- תצוגה שמורה מתוך ה־CRM
- segment דינמי לפי תוכנית, פעילות, סוג כלי, פרטי או עסקי, תאריך הרשמה, גרסת אפליקציה ופלטפורמה
- רשימת מזהים שיובאה באופן מבוקר
- כל המשתמשים הזכאים

לאחר הבחירה השרת ייצור audience preview ויציג בנפרד:

- משתמשים ייחודיים
- כתובות מייל תקינות
- מכשירי iOS ו־Android עם token פעיל
- משתמשים הזכאים להודעה באפליקציה
- החרגות לפי opt-out, חוסר פרטי קשר, פלטפורמה, כפילות או frequency cap

המסך יציג דוגמאות של נמענים ויאפשר לפתוח את הרשימה המלאה לפני שליחה. שינוי של תנאי הקהל יבטל את האישור הקודם ויחייב dry run חדש.

#### שלב 3: ערוצים ופלטפורמות

הערוצים יהיו מייל, Push, הודעת פעמון, banner או פופ־אפ. ליד כל ערוץ יוצגו מספר היעדים הזמינים והסיבה לחוסר התאמה. ב־Push ובהודעות גרסה תהיה בחירה מפורשת בין iOS ל־Android; ב־Web לא יוצגו אפשרויות native שאינן רלוונטיות.

ערוצים יהיו עצמאיים. `email`, `push` ו־`in_app` יקבלו delivery status נפרד, retry נפרד ו־Kill Switch נפרד. הודעה באפליקציה אינה תוצר לוואי של הצלחת המייל.

#### שלב 4: תוכן

המנהל יכתוב מסר בסיס אחד ולאחר מכן יוכל לבצע override לכל ערוץ:

- מייל: נושא, preheader, גוף, CTA ו־Reply-To
- Push: כותרת קצרה, גוף קצר ו־deep link
- פעמון: כותרת, גוף ויעד בתוך האפליקציה
- פופ־אפ או banner: כותרת, גוף, כפתורים, עיצוב ותנאי תצוגה

העורך ישתמש בשדות וברכיבי תוכן בטוחים. עריכת HTML ו־JSON תישאר מאחורי מצב מתקדם למנהלים מורשים בלבד. משתנים יוצגו כשדות בעלי שם מובן, עם ערכי דוגמה ואזהרה על משתנה חסר.

כל המחרוזות הממותגות יגיעו מ־`communicationBrandConfig` אחד: `Car Reminder`, שם השולח, כתובת שולח, Reply-To, כתובת העסק וקישורי החנויות.

#### שלב 5: תצוגה מקדימה ובדיקה

ה־preview יציג את אותו renderer שבו משתמש ערוץ היעד:

- מייל במחשב ובמובייל
- Push של iOS ו־Android
- הודעת פעמון בתוך האפליקציה
- פופ־אפ ב־Web ובמסך טלפון

„שלח בדיקה” יאפשר לבחור את המנהל הנוכחי, משתמש בדיקה שמור או כתובת ומכשיר מוגדרים. המערכת תמלא ערכי דוגמה בטופס רגיל ולא תחייב JSON. תוצאת הבדיקה תציג כל ערוץ בנפרד ואת מזהה המסירה.

#### שלב 6: תזמון ותדירות

- שליחה עכשיו או במועד עתידי
- אזור זמן מוצג במפורש
- שעות שקטות ל־Push
- תאריך תפוגה להודעה שאיבדה רלוונטיות
- פעם אחת, תדירות מוגבלת או אוטומציה חוזרת
- מניעת כפילות לפי campaign, משתמש וערוץ

לפני שליחה מיידית ייווצר audience snapshot קפוא. בקמפיין מתוזמן יוצג האם הקהל נקבע בזמן התזמון או מחושב מחדש בזמן השליחה; ברירת המחדל תהיה snapshot כדי שהכמות שאושרה היא הכמות שתישלח.

#### שלב 7: אישור

מסך הסיכום יציג במשפט אחד מה יקרה, לדוגמה: „הודעת טיפול מתוכנן תישלח מחר ב־09:00 ל־1,284 משתמשים: 1,172 מיילים, 946 הודעות פעמון ו־713 Push למכשירי Android”.

יופיעו גם:

- שם הקהל והפילטרים
- סוג ההודעה והבסיס החוקי להעדפות
- הערוצים והפלטפורמות
- כל ההחרגות
- קישורים ל־preview ולתוצאת בדיקת הניסיון
- שם המנהל שמפרסם

שליחה מעל סף שיוגדר, שליחה לכל המשתמשים או שינוי קהל לאחר בדיקה ידרשו אישור נוסף. אפשר להגדיר שמנהל אחד מכין ומנהל אחר מאשר קמפיין רחב.

### הודעה ישירה ושיחת לקוח

מתוך כרטיס לקוח או פנייה ה־composer ייפתח עם הנמען, החשבון והקשר הפנייה. ברירת המחדל תהיה הודעת שירות אישית עם מייל והודעה באפליקציה, אך המנהל יראה אילו ערוצים זמינים לפני השליחה.

לאחר השליחה תופיע רשומה אחת ב־timeline עם סטטוס לכל ערוץ. תגובת תמיכה לא תפתח `mailto:` ולא תסמן פנייה כנענתה בלחיצה. היא תישלח דרך המערכת, תיקשר לפנייה ורק לאחר הצלחה תעדכן `replied_at`, `replied_by` וסטטוס.

אם למשתמש אין חשבון, המייל יישלח לפי הכתובת שבפנייה. אם יש user ID אבל אין מייל תקין, ההודעה באפליקציה ו־Push עדיין יוכלו להישלח. כל ערוץ יפעל גם כאשר ערוץ אחר נכשל.

### רשימת קמפיינים ותוצאות

כל קמפיין יוצג עם סטטוס `draft`, `awaiting_approval`, `scheduled`, `sending`, `paused`, `completed`, `completed_with_errors`, `cancelled` או `failed`. הרשימה תציג מטרה, קהל, ערוצים, מפרסם, זמן ותוצאות מרכזיות.

עמוד קמפיין יפריד בין:

- משתמשים שנכללו בקהל
- ניסיונות מסירה לפי ערוץ
- נשלחו, נמסרו, נקראו, נפתחו, הוקלקו, נסגרו ונכשלו
- החרגות והסיבה להן
- ציר זמן של טיוטה, בדיקה, אישור, התחלה, עצירה וסיום

אין לחבר את כל הערוצים לאחוז אחד מטעה. פתיחת מייל, קריאת הודעת פעמון והקלקה בפופ־אפ הם מדדים שונים.

### הרשאות והגנות

- Support רשאי לשלוח הודעה אישית בלבד.
- Marketing רשאי להכין קמפיין, אך הרשאת פרסום לקהל רחב נפרדת.
- Operations רשאי לשלוח הודעות תפעוליות ולנהל אוטומציות מורשות.
- שינוי תבנית מערכת, Kill Switch או קמפיין לכל המשתמשים דורשים הרשאה מוגברת ו־audit.
- opt-out שיווקי והעדפות ערוץ נאכפים בצד השרת ב־dry run ובשליחה.
- הקהל, התוכן והגרסה שנשלחו נשמרים כ־snapshot לצורך audit.
- ביטול יעצור משימות שעדיין בתור; מסירות שכבר נשלחו לא יוצגו כאילו בוטלו.

### מודל נתונים הדרגתי

הטבלאות הקיימות של תבניות, triggers, `email_send_log`, אירועי Resend, `admin_popups` ו־`app_notifications` נשארות. מעליהן תתווסף שכבת orchestration:

```text
communication_campaigns
communication_audience_snapshots
communication_channel_content
communication_deliveries
communication_conversations
communication_messages
```

`communication_deliveries` תחזיק רשומה לכל campaign, משתמש וערוץ, ותפנה למזהה הספק הקיים. בשלב התאימות לוג המייל הקיים ימשיך להתעדכן, אך מסך המסירה החדש יקרא view מאוחד.

כל פעולות ה־UI יעברו commands מרכזיים: `previewAudience`, `saveDraft`, `sendTest`, `requestApproval`, `scheduleCampaign`, `startCampaign`, `pauseCampaign`, `cancelCampaign` ו־`sendDirectMessage`. המסכים לא יקראו ישירות ל־`send-email` או `dispatch-broadcast`.

### סדר מעבר בטוח

1. מאחדים את מסך השליחה הישירה ללא שינוי התשתית הקיימת.
2. מוסיפים תצוגה מקדימה אנושית למשתנים ומסירים JSON מזרימת ברירת המחדל.
3. בונים קהל preview בצד השרת ושומרים snapshot, תחילה עבור „כולם”.
4. מוסיפים segments ורשימות שמורות על נתוני ה־CRM.
5. מפרידים את `admin_direct` למשימות מסירה עצמאיות לכל ערוץ.
6. מוסיפים תזמון, אישור והרשאות לקמפיינים רחבים.
7. מאחדים את לוגי המסירה לתצוגה אחת ורק אז סוגרים את המסכים הישנים.

### בדיקות קבלה לתקשורת

- הודעה אישית מופיעה פעם אחת ב־timeline עם תוצאה נפרדת למייל, פעמון ו־Push.
- כשל Resend אינו מונע יצירת הודעה באפליקציה.
- פנייה אינה מסומנת כנענתה לפני שהתגובה נשלחה בהצלחה.
- dry run ופועל משתמשים באותו audience snapshot ומחזירים אותה כמות, למעט שינויי opt-out או פרטי קשר שנרשמים כהחרגה.
- משתמש שהסיר הסכמה לשיווק אינו נכנס לקמפיין שיווקי גם אם נבחר ידנית.
- קמפיין iOS אינו נשלח ל־Android של אותו משתמש.
- שינוי קהל או תוכן אחרי test מבטל את אישור הבדיקה ומחייב test חדש כאשר הכלל דורש זאת.
- לחיצה כפולה על „שלח” אינה יוצרת קמפיין או מסירה כפולים.
- ביטול קמפיין עוצר רק מסירות שטרם התחילו.
- כל preview משתמש בשם `Car Reminder` ובפרטי השולח המרכזיים.
- מנהל Support אינו יכול לפרסם לכל המשתמשים.
- ערך משתנה חסר נחסם לפני פרסום ומוצג בשם אנושי.
- סטטוס `completed_with_errors` מציג בדיוק אילו ערוצים ונמענים נכשלו ומאפשר retry ממוקד.

## מבנה מסך הגרסאות החדש

מסך הגרסאות יהיה תחת „תפעול ואבטחה > גרסאות ושחרורים”. בראשו יהיו שני טאבים עצמאיים: `iOS` ו־`Android`. מעבר בין הטאבים לא יעתיק טקסט, גרסה או סטטוס מהפלטפורמה האחרת.

### בכל טאב יוצגו

- הגרסה הפעילה בחנות
- הגרסה המינימלית הנתמכת
- מספר משתמשים ומכשירים בפלטפורמה
- התפלגות הגרסאות המותקנות
- סטטוס השחרור: טיוטה, ממתין לחנות, זמין בחנות, פורסם למשתמשים או הופסק
- מועד הפרסום האחרון ומי ביצע אותו
- תצוגה מקדימה של ההודעה כפי שתיראה במכשיר המתאים
- היסטוריית שחרורים של אותה פלטפורמה

### תוכן עצמאי לכל פלטפורמה

- מספר גרסה
- כותרת קצרה להתראת Push ולפעמון
- טקסט קצר להתראת העדכון
- כותרת „מה חדש”
- תוכן מלא של „מה חדש”
- קישור החנות המתאים
- בחירה אם העדכון רך או גרסת מינימום שחוסמת שימוש

### פעולות

1. שמירת טיוטה
2. תצוגה מקדימה
3. בדיקת נמענים ללא שליחה
4. סימון שהגרסה זמינה בחנות
5. פרסום למשתמשי הפלטפורמה
6. עריכה שקטה שאינה מציגה שוב הודעה למי שכבר ראה אותה
7. פרסום מחדש עם מזהה הודעה חדש
8. עצירת התראה בפלטפורמה אחת בלבד

הפעולה הראשית תציג תמיד את שם הפלטפורמה ואת מספר הגרסה, לדוגמה: „פרסם גרסת iOS 6.5.1”. לפני השליחה יוצגו מספר המשתמשים ומספר המכשירים שיקבלו Push.

```json
}
```

ה־RPC החדש יקבל `platform` בכל פרסום ויאמת שרק `ios` או `android` מותרים. בטווח הארוך עדיף להעביר היסטוריה לטבלת `platform_releases`, אך שני מפתחות additive ב־`app_config` מאפשרים מעבר ראשון קטן וללא שבירת הקוראים הקיימים.

### התאמות בצד המשתמש

- `useReleaseAnnouncement` יזהה פלטפורמה דרך Capacitor ויקרא רק את המפתח שלה.
- מפתח ה־seen המקומי יכלול פלטפורמה ומזהה הודעה.
- Web יחזיר `show: false` עבור הודעות שחרור native.
- `dispatch-push` יקבל את `data.platform` שכבר עובר בטריגר ויסנן את `device_tokens` בהתאם.
- `NotificationBell` ו־`Notifications` יסננו התראות `app_update` לפי הפלטפורמה הנוכחית.
- קישור החנות ייבנה מתוך `notification.data.platform`, ולא מתוך הפלטפורמה של המכשיר בלבד.

### תאימות לאחור

- כל עוד V2 כבוי, `release_announcement` הישן ממשיך לעבוד.
- בעת הפעלת הגרסה החדשה, קוראי V2 משתמשים רק במפתחות הפלטפורמה.
- לפני הפעלה מלאה מנקים או מקפיאים את ההודעה הגלובלית כדי למנוע הצגה כפולה.
- `android_latest_version`, `ios_latest_version`, `android_min_version` ו־`ios_min_version` נשארים ללא שינוי.
- `broadcast_app_update` הישן נשאר זמין ל־V1 עד השלמת המעבר.

## Rollback

החזרה לאחור אינה דורשת שינוי DB בשלבים הראשונים.

1. מכבים `VITE_ADMIN_CONSOLE_V2` בפריסה.
2. הנתיבים הישנים נשארים פעילים.
3. ה־commands וה־RPCs הישנים נשארים מקור הפעולה.
4. לא מוחקים רכיבי V1 עד שתי גרסאות לאחר המעבר.
5. שינוי סכימה עתידי חייב להיות additive תחילה: עמודות וטבלאות חדשות, בלי rename או drop באותו שחרור.
