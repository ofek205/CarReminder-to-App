# UX: אימות מחדש במחיקת חשבון

> שלב `ux` ב-Playbook. נכתב 2026-09-08. הבא בתור: `copywriter` על הקופי, ואז `frontend-design`.
> **הרקע:** [store-compliance-checklist.md §א-0](store-compliance-checklist.md), המחיקה שבורה ל-~92% מהמשתמשים.

---

## 1. UX Goal

שכל משתמש, לא משנה איך נרשם, יוכל למחוק את חשבונו **בעצמו, מתוך האפליקציה, בלי לפנות לתמיכה**, ויבין בדיוק מה נמחק לפני שהוא מאשר.

ובמקביל, שהאימות מול Apple ייראה למשתמש כמו **הוכחת זהות** ולא כמו צעד טכני מוזר, כי מבחינתו זה מה שהוא, גם אם בצד השרת הוא גם מספק את הקוד לביטול הטוקן.

## 2. User Flow

```
מסך בחירה (choose)
  ├─ "מחק את הנתונים שלי"      → mode='data'
  └─ "מחק את החשבון לצמיתות"   → mode='account'
        ↓
מסך אישור (confirm), הסדר החדש
  1. אזהרה: מה קורה
  2. רשימה: מה בדיוק יימחק
  3. שער אימות ← משתנה לפי provider
  4. פעולה
        ↓
   ┌────────────── ענף לפי provider ──────────────┐
   │ email          → סיסמה                       │
   │ apple + iOS    → גיליון נייטיב (Face ID)      │
   │ google / web   → הקלדת "מחק"                 │
   └───────────────────────────────────────────────┘
        ↓
   אימות נכשל → נשארים במסך, שגיאה ליד השער, שום דבר לא נמחק
   אימות עבר  ↓
        ↓
   [apple בלבד] ביטול טוקן, best-effort, שקוף למשתמש
        ↓
מוחק (deleting)
        ↓
   ├─ השרת חסם (בעלות עסקית) → חוזרים ל-confirm במצב חסום
   ├─ כשל אחר                 → חוזרים ל-confirm + "לא נמחק דבר"
   └─ הצליח                   → done
```

### נקודת הכרעה: איזה ענף

הסדר **אינו** "מה הכי נוח" אלא:

1. **יש identity של `apple` ואנחנו ב-iOS נייטיב → גיליון Apple.** גם אם למשתמש יש סיסמה. זה הענף היחיד שמחזיר את ה-`authorizationCode`, ובלעדיו אי-אפשר לבטל את הטוקן, דרישת 5.1.1(v).
2. אחרת, **יש identity של `email` → סיסמה.** ההוכחה החזקה ביותר שלא תלויה בצד שלישי.
3. אחרת → **הקלדת מילת אישור.**

**למה לא OAuth מלא בדפדפן:** `signInWithOAuth` עושה redirect, המסך נהרס, ו-`mode`/`step` נאבדים. חזרה מה-redirect לדף מחיקה ריק היא חוויה גרועה במיוחד בנתיב הרסני.

## 3. Screen Structure

### 3.1 מסך האישור: הסדר החדש

```
┌──────────────────────────────┐
│ ← חזרה                       │
├──────────────────────────────┤
│         ⚠  (אייקון)          │
│   בטוח שברצונך למחוק?        │  ← 1. מה קורה
│   לא ניתן לשחזר.             │
├──────────────────────────────┤
│  הנתונים הבאים יימחקו:       │  ← 2. מה יימחק
│  · כלי רכב וכלי שייט         │     (הועבר למעלה)
│  · מסמכים                    │
│  · טיפולים ותיקונים          │
│  · פוסטים ותגובות            │
│  · פרופיל ורישיון            │
│  · החשבון עצמו               │
├──────────────────────────────┤
│  ┌────────────────────────┐  │  ← 3. שער האימות
│  │  אישור זהות            │  │     ענף אחד מתוך שלושה
│  │  [סיסמה / Apple / מחק] │  │     בתוך כרטיס משלו
│  │  ↳ שגיאה כאן           │  │
│  └────────────────────────┘  │
├──────────────────────────────┤
│ [ מחק חשבון לצמיתות ]        │  ← 4. פעולה
│ [ ביטול ]                    │
└──────────────────────────────┘
```

**שלושה שינויים מבניים מול הקיים:**

1. **רשימת "מה יימחק" עולה מעל שער האימות.** אין הגיון לבקש מאדם להוכיח זהות לפני שהראינו לו מה הוא עומד לאבד. ליישר: להודיע → להבין → לאשר → לבצע.
2. **שער האימות עובר לכרטיס משלו** עם כותרת. הוא הופך מ-input תועה לצעד מפורש בזרימה, וההודעה על כשל אימות מופיעה **בתוך הכרטיס** ולא בראש המסך, ליד מה שנכשל.
3. **מצב חסום מחליף את השער, לא מתווסף אליו** (ראה 3.3).

### 3.2 שלושת ענפי השער

**א. סיסמה**: ללא שינוי פונקציונלי.
```
אישור זהות
הזן את הסיסמה שלך כדי לאשר
[ ················ ]  dir="ltr"
```

**ב. Apple ב-iOS נייטיב**
```
אישור זהות
כדי לאשר את המחיקה, נבקש ממך להזדהות מול Apple
[  אישור באמצעות Apple  ]   ← כפתור, 48px
```
לחיצה → גיליון נייטיב עם Face ID. אין שדה להקליד. **זה גם ה-thumb-reach הטוב ביותר מהשלושה**: כפתור אחד גדול, בלי מקלדת.

**ג. הקלדת מילת אישור**
```
אישור זהות
נרשמת דרך Google, ולכן אין סיסמה לאמת.
כדי לאשר, הקלד את המילה מחק
[ ········ ]
```
**למה מסבירים למה אין סיסמה:** בלי ההסבר, משתמש שמכיר מסך מחיקה עם סיסמה חושב שהאפליקציה שכחה אותה או שיש באג. שורה אחת מונעת קריאת תמיכה.

### 3.3 מצב חסום (בעלות עסקית)

**המצב הקיים מציג את החסימה ואת הטופס יחד. זה מוסר.** כשהשרת חוסם:

```
┌──────────────────────────────┐
│         🛡  (אייקון)          │
│  אי-אפשר למחוק כרגע          │
│                              │
│  אתה הבעלים של «שם החשבון»   │
│  ויש בו X חברים פעילים.      │
│  כדי למחוק, יש להעביר        │
│  קודם את הבעלות.             │
├──────────────────────────────┤
│ [ להעברת בעלות ]             │
│ [ חזרה ]                     │
└──────────────────────────────┘
```

**שער האימות וכפתור המחיקה נעלמים.** טופס שהשרת ידחה הוא הזמנה לתסכול. ושם החשבון מוצג **במלואו**: עקבי עם הכלל מאפיון החברות (ג14).

## 4. Component Recommendations

| תפקיד | קומפוננטה |
|---|---|
| כרטיס שער האימות | `Card` מ-`@/design/primitives` (variant `subtle`) |
| כפתור Apple | `CTAButton` variant `secondary`, גובה `lg` (48px) |
| כפתור מחיקה | `CTAButton` variant `destructive`, גובה `lg` |
| שדות קלט | ה-`input` הקיים בקובץ, לא להחליף, זה לא ה-scope |
| הודעת שגיאה בשער | `<p>` בתוך הכרטיס, `role="alert"` |
| מצב חסום | `EmptyState` מ-`@/design/primitives`, tone `warning` |

**לא להשתמש ב-`Dialog`**: המחיקה היא מסך עומד (`STANDALONE_PAGES`), לא מודאל. הוספת מודאל מעל מסך עומד תיצור שתי שכבות סגירה.

## 5. Interaction Principles

- **הכפתור לא disabled בלי הסבר.** כשאין קלט, הכפתור פעיל, והלחיצה מציגה שגיאה ליד השער. הבאג המקורי היה כפתור מושתק לנצח בלי סיבה מוצגת; אין לחזור עליו בצורה אחרת.
- **ביטול הגיליון של Apple אינו שגיאה.** משתמש שסגר את Face ID התחרט, חוזרים למסך בשקט, בלי הודעה אדומה.
- **הביטול מול אפל שקוף.** הוא best-effort; כשלון בו **אינו** נעצר ואינו מוצג. "לא הצלחנו לבטל את הטוקן מול Apple" הוא משפט שלא אומר למשתמש כלום ורק מפחיד אותו. הכשל נרשם ל-`app_errors`.
- **בזמן `deleting` אין דרך חזרה.** להסתיר את כפתור "חזרה", הפעולה אטומית בשרת וחזרה לא תעצור אותה.
- **נטישה באמצע אינה הרסנית.** אימות לבדו לא מוחק כלום; אין מה לנקות. ⚠️ אבל שני ענפי האימות **מחליפים את ה-session** (גם `signInWithPassword` וגם ה-authorize), התנהגות קיימת, לא רגרסיה, אבל צריך לוודא שהמסך לא נשבר על שינוי session באמצע.

## 6. Visual Hierarchy

1. **האזהרה**: הכי גדול, עם האייקון. אדום ל-`account`, ענבר ל-`data`.
2. **רשימת מה יימחק**: טקסט משני, אבל **לא אפור-עמום**. זה המידע שההחלטה מתבססת עליו.
3. **שער האימות**: כרטיס עם רקע נבדל. שם העין נעצרת אחרי הקריאה.
4. **כפתור המחיקה**: הפעולה, אבל **לא** האלמנט הבולט ביותר במסך. בנתיב הרסני האזהרה גוברת על הכפתור.
5. "ביטול" (נוכח, שקט).

## 7. States to Design

| מצב | מה מוצג |
|---|---|
| `choose` · default | שתי אפשרויות (קיים) |
| `confirm` · default | אזהרה + רשימה + שער לפי provider |
| `confirm` · provider נטען | ⚠️ **מצב חדש**: זהות ה-provider נקראת מ-`user`. עד שיש תשובה: skeleton בכרטיס השער, לא כפתור שקורס |
| `confirm` · אימות רץ | ספינר בכפתור, "מאמת..." |
| `confirm` · אימות נכשל | שגיאה **בתוך** כרטיס השער |
| `confirm` · חסום בעלות | שער וכפתור **מוסרים**, מוצג מצב חסום + CTA |
| `confirm` · offline | שער מושתק + "האימות דורש חיבור לאינטרנט" |
| `deleting` | ספינר, בלי חזרה |
| `deleting` · נכשל | חזרה ל-`confirm` + **"לא נמחק דבר"** |
| `done` | קיים |

**אין מצב `empty`**: המסך תמיד מוצג למשתמש מחובר עם נתונים או בלעדיהם; הרשימה סטטית.

## 8. Copy (סופי, אחרי `copywriter`)

**עקרון הטון:** מדויק, לא דרמטי. הסכנה כאן אמיתית, ולכן הקופי לא צריך להוסיף פחד אלא בהירות. אין סימני קריאה, אין "אזהרה!", אין הפחדה. עובדות, וכל הודעת שגיאה אומרת גם מה לעשות עכשיו.

### 8.1 שער האימות

| ענף | כותרת | הסבר | פעולה |
|---|---|---|---|
| סיסמה | אישור זהות | הזן את הסיסמה שלך כדי להמשיך | |
| Apple | אישור זהות | נבקש ממך להזדהות מול Apple לפני שנמשיך | הזדהה עם Apple |
| מילה | אישור זהות | נרשמת דרך Google, ולכן אין לך סיסמה באפליקציה. כדי להמשיך, הקלד את המילה **מחק** | |

**מה שונה מהטיוטה:** "כדי לאשר" הפך ל"כדי להמשיך". "לאשר" נשמע כמו הסוף, אבל השער הוא **אמצע** הזרימה, ואחריו עוד יש כפתור מחיקה. "להמשיך" מתאר נכון מה הלחיצה עושה ולא מבטיח יותר ממה שקורה.

בענף Apple הכפתור הוא **"הזדהה עם Apple"** ולא "אישור באמצעות Apple": פועל ראשון, וגם עקבי עם "המשך עם Apple" שכבר קיים במסך ההתחברות.

### 8.2 שגיאות

| מתי | קופי |
|---|---|
| סיסמה ריקה | יש להזין את הסיסמה כדי להמשיך |
| סיסמה שגויה | הסיסמה לא נכונה. בדוק ונסה שוב. |
| מילה לא הוקלדה | יש להקליד את המילה מחק |
| מילה שגויה | המילה לא תואמת. הקלד **מחק** בדיוק כפי שמופיע. |
| גיליון Apple נכשל | ההזדהות מול Apple לא הושלמה. נסה שוב. |
| גיליון Apple בוטל | *(אין הודעה, חזרה שקטה)* |
| אין חיבור | אין חיבור לאינטרנט. ההזדהות דורשת חיבור, נסה שוב כשהוא יחזור. |
| המחיקה נכשלה | המחיקה לא בוצעה ו**לא נמחק דבר**. נסה שוב, ואם זה חוזר כתוב לנו ל-support@car-reminder.app |

**"לא נמחק דבר" חייב להישאר.** ה-RPC אטומי (BEGIN/COMMIT אחד), ולכן זו אמירה נכונה, ובנתיב הרסני זו ההודעה שמונעת פאניקה ופנייה לתמיכה. שים לב לניסוח: **"המחיקה לא בוצעה"** ולא "המחיקה נכשלה". "נכשלה" משאיר את המשתמש בספק אם משהו קרה באמצע; "לא בוצעה" אומר במדויק שכלום לא זז.

**"הסיסמה לא נכונה"** ולא "סיסמה שגויה": "שגויה" נשמע כמו שיפוט על המשתמש, "לא נכונה" מתאר את העובדה. ו"בדוק ונסה שוב" נותן פעולה במקום להשאיר קיר.

### 8.3 מצב חסום (בעלות עסקית)

הקיים מציג כפתור סגול "להעברת בעלות" **בלי שום הסבר למה**. הנוסח החדש:

> ### אי-אפשר למחוק כרגע
> אתה הבעלים של **«שם החשבון»**, ויש בו {X} חברים פעילים.
> מחיקת החשבון שלך תשאיר אותם בלי גישה, ולכן צריך קודם להעביר את הבעלות למישהו אחר.
>
> **[ העבר בעלות ]**  **[ חזרה ]**

**ההוספה המרכזית היא ה"למה".** בלי המשפט על החברים שיישארו בלי גישה, החסימה נראית שרירותית והמשתמש חושב שהאפליקציה מקשה עליו בכוונה. עם ההסבר, החסימה נראית כמו הגנה על אנשים אחרים, וזה בדיוק מה שהיא.

**הכפתור:** "העבר בעלות" (פועל ראשון) ולא "להעברת בעלות" (שם פעולה). עקבי עם הנחיית הטון ב-`CTAButton`.

### 8.4 רשימת מה יימחק

| קיים | מומלץ | למה |
|---|---|---|
| כל כלי הרכב וכלי השייט | כל הרכבים וכלי השייט | "כלי הרכב" מסורבל; "הרכבים" זה מה שאומרים |
| מסמכים (ביטוח, רישיון, וכו') | מסמכים: ביטוח, רישיון ועוד | "וכו'" חלש ופקידותי |
| טיפולים ותיקונים | טיפולים ותיקונים | ✔ |
| פוסטים ותגובות בקהילה | פוסטים ותגובות בקהילה | ✔ |
| לייקים ושמירות | לייקים ופריטים שמורים | "שמירות" דו-משמעי |
| פרופיל אישי ורישיון נהיגה | הפרופיל ורישיון הנהיגה | ✔ |
| החשבון עצמו (ייסגר) | **החשבון עצמו** | הסוגריים מיותרים, המודגש עושה את העבודה |

**והרשימה צריכה תבליטים אמיתיים.** הקיים מדפיס `-` בתוך `<ul>`, כלומר מקף ידני בתוך רשימה. `list-disc` ואז בלי המקף.

### 8.5 קופי שאר המסך

| מקום | קיים | מומלץ |
|---|---|---|
| כותרת הבחירה | מחיקת חשבון ונתונים | ✔ |
| תת-כותרת | CarReminder מאפשרת לך למחוק את הנתונים שלך בכל עת. בחר מה ברצונך לעשות: | אפשר למחוק את הנתונים או את החשבון כולו, בכל עת. בחר מה לעשות: |
| אישור, mode=account | בטוח שברצונך למחוק את החשבון? | למחוק את החשבון לצמיתות? |
| אישור, mode=data | בטוח שברצונך למחוק את כל הנתונים? | למחוק את כל הנתונים? |
| כרטיס account | ...לא ניתן לשחזר. תנותק מהמערכת. | ...לא ניתן לשחזר, ותנותק מהאפליקציה. |
| מוחק, account | מוחק נתונים... | מוחק את החשבון... |
| מוחק, data | מוחק נתונים... | מוחק את הנתונים... |

**"ברצונך" יורד.** זו עברית פקידותית שאף אחד לא מדבר. "למחוק את החשבון לצמיתות?" קצר יותר, ישיר יותר, ו**הפועל בהתחלה** מה שמתאים לסריקה במובייל.

**"תנותק מהמערכת" הופך ל"תנותק מהאפליקציה".** "המערכת" היא מילה של ספק תוכנה שמדבר על עצמו, לא של אפליקציה צרכנית.

**"מוחק נתונים..." מסתעף לפי mode.** משתמש שבחר למחוק חשבון ורואה "מוחק נתונים" עלול לחשוב שבחר באפשרות הלא נכונה, ברגע היחיד שבו אי-אפשר לחזור.

## 9. UX Risks

| סיכון | הפחתה |
|---|---|
| משתמש עם Apple **וגם** סיסמה יופנה לגיליון ולא יבין למה לא נשאלה סיסמה | ההסבר בשער מנוסח סביב "הזדהות" ולא סביב "סיסמה", ולכן אין ציפייה שנשברת |
| ה-`authorizationCode` יגיע ריק והביטול ייכשל בשקט | אין השפעה על המשתמש (best-effort), אבל **חייב** להירשם ל-`app_errors` אחרת לא נדע שהציות שבור |
| Apple ב-**דפדפן** (מסלול נדיר אך קיים) | נופל לענף מילת האישור. המחיקה עובדת; הטוקן לא מבוטל, ונרשם |
| 8 המשתמשים הקיימים | **כן** נתמכים, האימות מייצר קוד טרי, ולכן אין בעיית מיגרציה. זה היתרון המרכזי של הגישה |
| "מחק" כמילת אישור עלול להיות מתורגם/מוקלד עם רווח | להשוות אחרי `trim()`, ולא case-sensitive |
| המשתמש לא ישים לב שהרשימה עלתה למעלה ויחפש את הסיסמה | הכרטיס עם הכותרת "אישור זהות" בולט מספיק; ההודעה על כשל בתוכו |

## 10. מה במפורש **לא** ב-scope

- החלפת ה-`input` הקיים בקומפוננטת עיצוב חדשה
- שינוי מסך `choose`, `deleting` ו-`done`
- ההסכמה המפורשת ל-AI (א-2), flow נפרד
- שינוי ב-`delete_my_account` עצמו
