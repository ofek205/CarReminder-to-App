# UX: סינכרון דו-כיווני בין הבורר להדגמה

> שלב `ux`. קודמו: [spec](spec-marketing-demo-two-way-sync.md). הבא: `designer`.
> נכתב 2026-09-10.

## 1. יעד החוויה

שהבורר יפסיק להיות מחליף-תמונות ויהיה **שלט של המכשיר שלידו**. המבקר בוחר מה
לראות, רואה את זה קורה, וקורא הסבר שתואם למה שעל המסך. ובכיוון ההפוך: כשהוא
נוגע במכשיר, הטקסט בצד עוקב אחריו במקום להשאיר אותו לנחש מה הוא רואה.

## 2. העיקרון היחיד שכל השאר נגזר ממנו

> **הסימון תמיד אומר דבר אחד: „זה מה שהמכשיר מציג עכשיו”.**

לא „זה מה שבחרת”, לא „זה מה שנלחץ אחרון”. הצהרה על מצב המכשיר.

זה נראה כמו עניין סמנטי והוא מכריע ארבע שאלות בלי דיון:

- **לחיצה בזמן טעינה** לא מזיזה את הסימון, כי המכשיר עוד לא מציג את זה.
- **שלוש לחיצות מהירות** מזיזות את הסימון פעם אחת, כשהמכשיר מגיע.
- **ניווט בתוך המסגרת** מזיז את הסימון, כי המכשיר באמת שם.
- **ניווט למסך שאינו בחמישה** מנקה את הסימון, כי אף פריט אינו מה שמוצג.

### רוויזיה ל-S9 במפרט

המפרט ביקש לשמור את הסימון האחרון בניווט מחוץ לחמישה. **אני משנה את זה**:
לשמור סימון על פריט שאינו מה שמוצג הוא שקר קטן שמלמד את המבקר שהסימון לא אמין,
וברגע שהוא לא אמין הכיוון ההפוך מאבד את כל הערך שלו. הסימון מתנקה, וההסבר עובר
לשורה ניטרלית שמכירה במקום שבו המבקר נמצא. זה כנה, וזה מתקן את עצמו בלחיצה אחת.

## 3. זרימה

```
הקטע נכנס למסך
   └─ ההדגמה נטענת לבד, נפתחת ב-/Dashboard
      └─ „מה מתקרב” מסומן, ההסבר שלו מוצג        ← מסונכרן בשנייה אפס

המבקר לוחץ על פריט
   ├─ המסגרת חיה  → המסגרת מנווטת → הסימון וההסבר עוברים
   ├─ המסגרת נטענת → הפריט נכנס למצב „ממתין”, הסימון לא זז.
   │                  כשהמסגרת עולה היא הולכת לשם, והסימון נוחת
   ├─ אין הדגמה    → מתנהג כמו היום: מחליף צילום והסבר
   └─ מובייל       → בנוסף: המכשיר נגלל לתוך המסך (סעיף 6)

המבקר נוגע בניווט בתוך המסגרת
   ├─ הגיע לאחד מהחמישה     → הסימון וההסבר עוברים אליו
   ├─ הגיע למסך אחר          → הסימון מתנקה, הסבר ניטרלי
   └─ הגיע למסך כתיבה        → הפופ-אפ, חזרה ל-/Dashboard,
                                והסימון עוקב חזרה ל„מה מתקרב”
```

## 4. מבנה

### דסקטופ, RTL. הבורר מימין לטקסט, המכשיר משמאל

```
┌──────────────────────────────────────────────────────┐
│                                    המסכים שתשתמשו בהם │
│  ┌───────────────┐   כותרת ההסבר של המסך המסומן        │
│  │ ╭───────────╮ │   הפסקה שמסבירה בדיוק את המסך הזה   │
│  │ │ הדגמה   ✕ │ │                                     │
│  │ ├───────────┤ │   ● מה מתקרב                    ←   │
│  │ │           │ │   ○ הרכבים שלי                  ←   │
│  │ │ האפליקציה │ │   ○ כרטיס רכב                   ←   │
│  │ │   החיה    │ │   ○ המסמכים שלי                 ←   │
│  │ │           │ │   ○ כלי שייט                    ←   │
│  │ ╰───────────╯ │                                     │
│  └───────────────┘   ✓ יתרון    ✓ יתרון                │
│  הנתונים להמחשה בלבד                                   │
└──────────────────────────────────────────────────────┘
```

הרשימה נשארת עמודה אחת אנכית. חמישה פריטים בגובה נוח, החץ נשאר כאפורדנס של
„עבור לשם”, וזה כבר קורא נכון בתור שלט.

### מובייל: הבורר הופך לרצועת צ׳יפים בגלילה אופקית

```
┌─────────────────────────┐
│  המסכים שתשתמשו בהם     │
│  כותרת ההסבר            │
│  פסקת ההסבר             │
│                         │
│ ┌──────────────────────┐│  ← רצועה אחת, גלילה אופקית
│ │●מה מתקרב│○הרכבים│○כר…││     הצ׳יפ הפעיל נגלל לתצוגה
│ └──────────────────────┘│
│                         │
│   ╭─────────────────╮   │
│   │  הדגמה       ✕  │   │
│   ├─────────────────┤   │
│   │   האפליקציה     │   │
│   │     החיה        │   │
│   ╰─────────────────╯   │
└─────────────────────────┘
```

**למה זה מחליף את הגריד של 3+2:** חמישה פריטים ב-`repeat(3,1fr)` נותנים שורה
אחרונה חצי ריקה, ובלחיצה על מסך צר הם מצטמצמים ל-12px בלי אייקונים ועם ריפוד
של 5px לצדדים. זה היה נסבל כשהבורר החליף תמונה. עכשיו הוא **הניווט הראשי של
ההדגמה**, ואזור מגע דחוק בשורה קטועה הוא הדבר הלא נכון לתת לו.

רצועה אופקית פותרת שלוש בעיות בבת אחת: אין שורה קטועה, כל צ׳יפ מקבל רוחב אמיתי
עם גובה מגע של 44px, והרצועה תופסת שורה אחת בלבד ולכן **המכשיר נשאר קרוב**.
ובונוס שמתחבר לכיוון ההפוך: כשהמכשיר מנווט, הרצועה גוללת את הצ׳יפ הפעיל לתצוגה,
כך שהמבקר רואה את הסימון זז גם אם הוא היה מחוץ לתצוגה.

## 5. מצבים לעיצוב

| מצב | הבורר | ההסבר | המכשיר |
|---|---|---|---|
| **ברירת מחדל** (חי, מסונכרן) | פריט אחד מסומן | ההסבר של המסומן | האפליקציה החיה |
| **טעינה** (המסגרת עולה) | אין סימון פעיל. פריט שנלחץ במצב „ממתין” | ההסבר של הפריט הממתין | שלד מתחת לצילום |
| **ממתין** (נלחץ בזמן טעינה) | הפריט מסומן כממתין, לא כפעיל | של הפריט הממתין | לא זז עוד |
| **מחוץ לחמישה** | **אין סימון** | שורה ניטרלית | האפליקציה החיה |
| **כישלון** | מתנהג כמו היום | של הפריט הנבחר | צילום סטטי, בלי סרגל |
| **נסגר** | מתנהג כמו היום | של הפריט הנבחר | צילום סטטי |
| **אופליין** | מתנהג כמו היום | של הפריט הנבחר | צילום סטטי |
| **מסך כתיבה** | חוזר ל„מה מתקרב” אחרי החזרה | של „מה מתקרב” | פופ-אפ ואז דף הבית |
| **ריק** | לא קיים. חמישה פריטים קבועים בקוד | — | — |

„ריק” לא רלוונטי כאן במכוון: הרשימה קבועה ולא נטענת מנתונים, ולכן אין מצב שבו
אין פריטים. אמרתי את זה במפורש כדי שלא ייראה כמו מצב שדילגתי עליו.

## 6. עקרונות אינטראקציה

**המכשיר נגלל לתצוגה במובייל.** במובייל הגריד מתקפל לעמודה אחת, והבורר יושב
ב-DOM **לפני** המכשיר, כלומר מעליו. בלי טיפול, לחיצה על צ׳יפ משנה משהו **מתחת
לקיפול** והמבקר לא רואה שקרה משהו. לכן לחיצה במובייל גוללת בעדינות את המסגרת
לתצוגה. תחת `prefers-reduced-motion` הגלילה מיידית ולא מונפשת.

**לחיצה על הפריט שכבר מסומן אינה לחיצה מתה.** במובייל היא גוללת את המכשיר
לתצוגה, וזה בדיוק מה שמבקר שאיבד אותו ירצה. בדסקטופ, שבו המכשיר תמיד נראה, היא
לא עושה כלום ובצדק.

**תקציב ההשהיה בכיוון ההפוך: 300ms.** מעבר לזה הסימון מרגיש מנותק מהמכשיר ולא
עוקב אחריו. זו דרישה ל-`frontend-design`, לא בקשה.

**הפוקוס לא נכנס למסגרת.** אחרי לחיצה הפוקוס נשאר על הכפתור. מקלדת שנופלת לתוך
ה-iframe נתקעת שם מאחורי מלכודת הפוקוס שלו, וזו בדיוק הסיבה שכפתור הסגירה יושב
מחוץ למסגרת.

**מקלדת:** חמשת הכפתורים בסדר ה-Tab. `Enter` ו-`Space` מפעילים, כמו כל כפתור.
ניווט בחצים בתוך הקבוצה הוא nice-to-have ולא חובה, כי חמישה פריטים ב-Tab זה
מרחק סביר.

**מעבר בין מסכים במסגרת:** בלי אנימציה מצדנו. האפליקציה מרנדרת מסך חדש והשלד
לא חוזר; הבהוב של שלד על כל החלפת מסך היה גורם להדגמה להרגיש איטית משהיא.

## 7. היררכיה

הסדר בעין, מלמעלה: **כותרת ההסבר** (היא מה שמשתנה ולכן היא העוגן), אחריה
**הפסקה**, אחריה **הבורר**, ואחרון המכשיר, שהוא ממילא הדבר הגדול והנע ולכן
מושך תשומת לב בלי עזרה.

הסימון הפעיל צריך להיות **המקום הכי בולט בתוך הבורר** ולא סתם רקע לבן: הוא
עכשיו מדווח מצב מכשיר ולא בחירה, ומצב שלא רואים ממטר לא מדווח כלום. הפרטים
של איך, ל-`designer`.

## 8. סיכוני UX

| סיכון | הפחתה |
|---|---|
| **במובייל השינוי קורה מתחת לקיפול** ולכן נראה כאילו הלחיצה לא עשתה כלום | גלילת המכשיר לתצוגה, סעיף 6. זהו הסיכון הגדול ביותר כאן |
| הסימון והמצב „ממתין” ייראו אותו דבר, והמבקר יחשוב שהמכשיר כבר שם | שני מצבים ויזואליים נפרדים לגמרי. ל-`designer` |
| ניקוי הסימון ייראה כמו תקלה | שורה ניטרלית שמכירה במקום שבו המבקר נמצא, ולא אזור הסבר ריק. ל-`copywriter` |
| רצועה אופקית מסתירה שיש עוד פריטים מימין | חיתוך חלקי של הצ׳יפ הבא בקצה, שמראה שיש המשך. ל-`designer` |
| הבורר ייראה כמו טאבים של האתר ולא כשלט של המכשיר | החץ נשאר, והקרבה הוויזואלית למכשיר עושה את העבודה |

## 9. מה עובר הלאה

→ **`designer`**: הסימון הפעיל מול „ממתין” מול לא-מסומן, רצועת הצ׳יפים במובייל
כולל רמז ההמשך, והבלטת הסימון עכשיו שהוא מדווח מצב.

→ **`copywriter`**: חמש כותרות וחמש פסקאות **שמתארות את המסך האמיתי** ולא פיצ׳ר
כללי (שתיים מהחמש חדשות: „כרטיס רכב” ו„כלי שייט”), והשורה הניטרלית למצב
מחוץ-לחמישה.
